# CLAUDE.md — SkillBridge (First Commit Hackathon)

Multi-tenant, voice-first, multilingual vocational upskilling SaaS for India's blue-collar workforce, demoed on one vertical: industrial mechanical/electrical maintenance. Learning plans are AI-curated per profession and grounded in each organization's own private SOPs.

Four facts frame everything below:

- **Strictly B2B.** Organizations subscribe and onboard their workers. There is no consumer or self-serve path, no sign-up screen, and `orgId` is present on every item, every token and every request — never null, never a sentinel, never defaulted.
- **One region: `ap-northeast-1`.** Deliberate. It is the only bootstrapped region and the only place the Bedrock inference profiles resolve.
- **Exactly three backend surfaces reach the browser.** CRUD via Next.js route handlers under `web/src/app/api/`; voice via the App Runner WebSocket; agents via the AgentCore Gateway. There is no fourth.
- **Scaffolding is done.** The stacks, the route files, the voice service modules and the key builders all exist. Implement *into* them; do not regenerate, re-init, or build alongside.

## Scope and process

**Finish the voice loop first.** Mic → Sarvam `saaras:v3-realtime` → Bedrock Haiku 4.5 (streamed) → Sarvam `bulbul:v3` → speaker, wired to the viewer's `onPartSelected(hotspotId)` so tap-a-part-and-ask works end to end on one model. No other BUILD feature — assessments, manager dashboard, admin flows, badges — starts before that works. This is the demo moment and the single differentiator.

**Build order.** Infrastructure bottom-up, then the voice slice, then the web tier:

1. **CDK foundation in dependency order: security (KMS) → data (table + buckets) → auth (Cognito, role groups, SMS/email).** Security precedes data because `infra/bin/infra.ts` constructs `SecurityStack` first and passes `security.dataKey` into `DataStack` — the reverse order cannot execute.
2. IAM and the four per-agent roles.
3. Bedrock: per-org Knowledge Base + vector store, AgentCore Gateway + Identity, Cedar policy store, Strands agent definitions.
4. **Voice service.** It is the only separately deployable backend — a persistent App Runner process with its own image — so it deploys and is endpoint-tested on its own, before any web work.
5. **CRUD routes and the frontend are one deployable, not two phases.** Decision 2 puts CRUD in Next.js server routes, so there is no backend to deploy and verify ahead of the UI for that surface. Implement each route handler and verify it with direct HTTP calls against `next dev` (or a preview deploy) *before* building the page that consumes it — but do not plan a separate "backend deploy, then backend endpoint testing, then frontend" phase for CRUD. That sequence only applies to the voice service.
6. i18n, PWA and accessibility mode across the pages.
7. Role-group end-to-end passes: worker, manager, admin.
8. Amplify deploy, then full end-to-end.

**The demo spine is never cut, stubbed or deferred:** org admin invite → worker onboarding → generated learning plan → lesson with a 3D machine model → tap a part and ask by voice, answered from the org KB in the worker's language → assessment → progress.

**When time runs short, cut in FEATURES.md's order and stop as soon as the spine is safe:** (1) manager aggregate dashboard → static stub; (2) admin billing/department flows → schema + Cedar only, demoed as mockups; (3) fast-track path → folded into the general plan; (4) badges → display-only, no award logic; (5) diagnostic trainer → folded into the general tutor loop; (6) 3D library → one model, tap-a-part still working; (7) assessment formats → keep `diagnose-by-voice` only; (8) UI languages → 2–3 live. Cut screens must look visibly non-functional, not half-wired.

**Build nothing from the PITCH list, and ship no UI affordance that implies it.** Forbidden: three.js / react-three-fiber or any physics or live-schematic simulation; CAD (STEP/SolidWorks) ingestion; an AR button; Rekognition or any vision/image assessment; Amazon Connect or IVR; Stripe, Marketplace metering or a working billing console; formal certificates; AgentCore Memory or Evaluations; a fifth agent; a content-moderation workflow beyond the manager re-verify warnings; soft-skills or digital-literacy modules; offline sync beyond the PWA shell; SSO or domain provisioning; any locale outside `LOCALES` in `web/src/i18n/config.ts` (en, hi, mr). ## Tenancy, auth and RBAC

`orgId` is the only tenant boundary in this design, and every builder in `keys.ts` takes it as a plain string and validates nothing. One caller-supplied `orgId` reaching `orgPk()` is a complete cross-tenant read with no second bug required.

- **`orgId`, `userId` and `role` come only from verified Cognito claims, resolved server-side.** Never from a request body, query string, path segment or client-set header — not even temporarily to unblock a route. No `orgId` parameter is exposed on any `/api/*` route. Reject a token carrying no `orgId`; never default or synthesise one.
- **Write one server-side resolver and route every handler through it.** There is no auth helper in `web/src/lib/` today (only `amplify.ts`, `ddb.ts`, `keys.ts`, `types.ts`), and all six API handlers are bare stubs, so the wrong pattern is currently the path of least resistance. Create exactly one `requireSession(role?)` returning `{ userId, orgId, role }`.
- **Cedar authorizes the AgentCore Gateway only.** It never sees a Next.js request. FEATURES says roles are "not an app-level `if (role === …)` check" — that is true for agent handlers and tool code, where role checks must live in Cedar policies with worker/manager/admin as subjects. It is not true for the CRUD routes, which bypass the Gateway entirely and must verify session, role and `orgId` themselves. Under time pressure, cut elaborate Cedar rules first; never cut Gateway JWT verification.
- **Cognito access tokens do not carry `custom:*` attributes** — only `sub`, `client_id`, `scope`, `token_use`, `username` and `cognito:groups`. `services/voice/src/auth/cognito.ts` is hardcoded to `tokenUse: 'access'` while `VoiceUser` requires `orgId`, so the naive implementation compiles, runs, and authorizes turns with `orgId === undefined`. Resolve this before writing `verifyToken()`: verify the **ID token** (carries the declared `custom:*` attributes, free), and/or take `role` from `cognito:groups` (AuthStack already creates a group per role) and load `orgId` from `USER#<sub>` / `PROFILE`. A pre-token-generation V2 trigger is the expensive branch — it needs a user pool feature plan AuthStack does not set. Decode a real token and confirm the claim before building on it. Never fix this by reading `orgId` from the request.
- **Add explicit `writeAttributes` to the `WebClient` app client that exclude `custom:orgId`, `custom:deptId` and `custom:role`.** `addClient('WebClient', {...})` sets no attribute allowlist today, and an unspecified allowlist grants write access to every mutable attribute — all seven are `mutable: true`. As scaffolded, any signed-in worker can call `updateUserAttributes({'custom:role':'admin','custom:orgId':'<other org>'})`. This is the one live privilege-escalation hole in the current code. Onboarding preferences persist to `USER#<id>` / `SETTINGS`, so these need not be client-writable at all. If you also set `readAttributes`, list every attribute the client actually needs — it narrows reads.
- **Never call Amplify `signUp`/`confirmSignUp` or render a registration form.** `selfSignUpEnabled: false` makes any client-side SignUp fail at runtime. Accounts are created only server-side during invite redemption: `AdminCreateUser` with `MessageAction: 'SUPPRESS'` (the invite already carried the code), `AdminAddUserToGroup`, then `AdminSetUserPassword` with `Permanent: true` — otherwise the user lands in FORCE_CHANGE_PASSWORD and the next `signIn` returns a challenge instead of a session. Set `phone_number` **or** `email`; never require email, since most of this workforce has no domain address.
- **Invite redemption order:** GSI2 lookup on `INVITE#<code>` → conditional `UpdateItem` on `ORG#<orgId>` / `INVITE#<code>` marking it redeemed, guarded on not-already-redeemed **and** `expiresAt` → only then create the Cognito user, copying `orgId`/`deptId`/`role` from the invite item, never from the request. Generate codes with `crypto.randomBytes`, not a counter or short slug. Trap: `Invite.redeemedAt` is typed `string | null` and `ddb.ts` sets `removeUndefinedValues: true`, which strips `undefined` but preserves `null` — so if issuing writes `redeemedAt: null`, the attribute exists and `attribute_not_exists(redeemedAt)` never fails, permitting unlimited redemptions of one code. Omit the attribute at issue time, or condition on `attribute_type(redeemedAt, NULL)`.
- **The Cognito `sub` is the `userId`, verbatim, everywhere.** Create the Cognito user first, then write `USER#<sub>` / `PROFILE` with the returned sub. Never mint an application-side user id (no ULID), and never add a GSI for email or phone lookup — that lookup path is deliberately omitted.
- **Never write `if (orgId === null)` or a nullable `orgId` type.** But `deptId` stays nullable and the `DEPT#NONE` sentinel in `gsi1.sk` stays. Decision 0's "never a sentinel" is about the tenant, not the department; deleting the `?? 'NONE'` breaks GSI1 `begins_with` for exactly the users an admin has just invited and not yet placed.
- **Treat `customAttributes` in `auth-stack.ts` as append-only.** Never rename, retype, resize or flip `mutable` on the existing seven. Cognito rejects schema changes to existing custom attributes, so CDK would force a pool replacement — and `removalPolicy: DESTROY` means the replacement deletes every provisioned worker, invalidates all tokens and orphans every `USER#<sub>` item. If a change is rejected, do not destroy and recreate the pool.

## Data model — single-table `AppTable`

- **Build every PK/SK/GSI key through `web/src/lib/keys.ts`** (`keys.*`, `gsi1.*`, `gsi2.*`, `orgPk`, `userPk`, `eventTtl`). Never write a `USER#`/`ORG#`/`EVT#`/`AGG#`/`CACHE#`/`SKILLPROFILE#` template literal inline. `services/voice` and the AiStack Lambdas have no copy of this module — vendor it verbatim (it has zero imports, so it copies cleanly) rather than re-typing strings. A drifted literal (`SKILLPROFILE` vs `SKILLPROFILE#CURRENT`) writes an item nothing ever reads back, with no error. `EVENT_TTL_DAYS = 90` is duplicated in `infra/lib/config.ts` and `keys.ts`; change both together.
- **Set `orgId` explicitly on every item written.** `ddb.ts` sets `removeUndefinedValues: true` and will drop it silently, producing an item that fails every isolation check. On any read that reaches a `USER#<userId>` partition for a caller other than that user (manager drill-down M4, admin flows, agent tool calls), compare the item's `orgId` against the caller's claim and reject on mismatch. `USER#<userId>` keys contain no orgId, so a bare userId reads across tenants — "the request supplied a userId" is never authorization.
- **Place new item types by write volume, not ownership.** Written once per worker action, per voice turn or per cache miss → `USER#<userId>` or its own hashed partition (`CACHE#<orgId>#<hash>`). `ORG#<orgId>` takes only bounded, read-heavy config and content: META, SUB, DEPT#, INVITE#, DOC#, LESSON#, ASMT#, ASSET#, AGG#. One org partition caps around 3,000 RCU / 1,000 WCU; a per-worker write under ORG# makes the whole workforce contend for it. If you are about to add a per-worker or per-event item under ORG#, you are making the mistake the split exists to prevent.
- **Any value derived from many items is a materialized `AGG#…` item**: written by the async/stream path with `UpdateItem` + `ADD` (or `SET x = if_not_exists(x, :0) + :n`), read with exactly one GetItem. Never GetItem-then-PutItem an aggregate, never recompute from a scan, and never let a route handler query GSI1 and loop GetItems per worker to build a dashboard number. Read-modify-write also loses counts: the profiler consumes SQS batches of 10 with concurrent invocations. This applies to every future aggregate — pass rates, cohort trends, org counts — not just the department rollup. If the UI needs a number the aggregate does not carry, add it to the profiler's write path, not the read path.
- **GSI1 is sparse.** Write `GSI1PK`/`GSI1SK` only on the `USER#<userId>` / `PROFILE` item, never on any other type — every item carries `orgId`, and projecting them all would clone the table into one per-org index partition and reintroduce the hot partition on the write side. Recompute `GSI1SK` with `gsi1.sk()` in the same `UpdateItem` that changes a user's `role` or `deptId`; a stale value makes manager department listings return wrong membership with no error. Unassigned users are found with `gsi1.deptPrefix('NONE')`, not by omitting the key.
- **Only GSI1 and GSI2 exist.** `infra/lib/data-stack.ts` does not create GSI3, though DATA-MODEL.md describes it as optional/cuttable — querying it fails at runtime with a ValidationException. List org content via base-table `begins_with` (`DOC#`, `LESSON#`, `ASMT#`, `ASSET#`) and sort in the handler. If a genuinely new access pattern needs an index, add it to `data-stack.ts` and DATA-MODEL.md in the same change.
- **Every `EVT#` and `CACHE#` put carries an attribute named exactly `ttl`, from `eventTtl()` called with no argument.** Not `expiresAt`, not `TTL`, not milliseconds. The table declares `timeToLiveAttribute: 'ttl'`, so any other name is silently ignored and raw query/activity events become a permanent record. `eventTtl` already returns epoch seconds; passing it a seconds value pushes expiry ~50,000 years out.
- **Every timestamp embedded in a sort key** (`EVT#<ts>#<ulid>`, `SESSION#<ts>#<sessionId>`, `ATTEMPT#<assessmentId>#<ts>`) must be a lexicographically sortable ISO-8601 UTC string. All three builders take `ts: string` and will accept garbage. The profiler's only read is the `SK between EVT#<from> and EVT#<to>` range query, and attempt history depends on SK ordering.
- **Zero-pad `seq` in `PLAN#<planId>#MOD#<seq>`** — fix it inside `keys.planModule`, which currently interpolates a raw `number`, or sort by the `seq` attribute after the Query. Unpadded, `MOD#10` sorts before `MOD#2`, so any plan with ten or more modules comes back out of order and the worker sees module 10 before module 2.
- **Key the RAG cache exactly as `keys.ragCache()` builds it**: `PK = CACHE#<orgId>#<questionHash>`, `SK = KB#<kbVersion>`, with a `ttl` attribute. Read with an exact GetItem. Never cache on the question hash alone, never share an entry across orgs, never Query the partition without pinning the `KB#<kbVersion>` sort key, and never move this cache under `ORG#<orgId>`. Invalidation is by bumping the org's `kbVersion` on KB rebuild — there is no purge path, and none should be written.
- **Writes are stream-driven, never on the request path.** `EVT#` and `SESSION#` items are written fire-and-forget; never `await` a DynamoDB call inside `services/voice/src/voice/turn.ts` or `channel.ts`, and never block a frame on one. These writes go through the App Runner service role (read/write), not the AiStack `VoiceOrchestratorRole` (read-only, which will throw AccessDenied on a PutItem).
- **Do not implement the §9 access audit trail as `EVT#` items.** `EventStreamFanout` filters on the `EVT#` prefix and enqueues profiling work, so audit records written that way both expire on the 90-day TTL and pollute profiler input with Bedrock spend attached. Write audit entries as a distinct item type with no `ttl` from the Next.js routes, and/or enable CloudTrail S3 data events on `OrgDocsBucket`.

## Infrastructure — CDK

- **Every stack gets `env: { account: process.env.CDK_DEFAULT_ACCOUNT, region: REGION }`,** with `REGION` imported from `infra/lib/config.ts`. Never declare an env-agnostic stack, never read `CDK_DEFAULT_REGION`, never add a second region or a cross-region construct (replica table, cross-region replication). Only ap-northeast-1 is bootstrapped, and `this.region` is what builds the Bedrock ARNs in ai-stack and compute-stack.
- **The stack roster is exactly six** — security, data, auth, ai, compute, web — each named with `stackName('<suffix>')`. Put a new resource in the stack that already owns its layer (KMS→security, table/buckets→data, Cognito→auth, agent roles + async pipelines→ai, ECR/App Runner→compute, Amplify→web) rather than adding a seventh. Derive any explicit physical name from `APP_NAME`. `config.ts` is the only naming authority; the default single `InfraStack` was deleted deliberately for this split.
- **Do not create per-organization resources in CDK.** Per-org KMS CMKs, per-org Knowledge Bases and their `org=<orgId>/docs/` data sources, and per-org Cedar policy bindings are created by the application at org-provisioning time. CDK holds only what exists before any tenant does: the account-level `alias/skillbridge-data` key and the two shared buckets. FEATURES §9 reads as "add them to the stack" — it is not; putting them there would make onboarding a customer require a `cdk deploy` and grow the template per tenant. Both `security-stack.ts` and `ai-stack.ts` say so in comments.
- **Source every Bedrock model id from `MODELS` in `infra/lib/config.ts`** — never inline one in a stack — and grant it through the existing `bedrockInvoke()` helper, with only `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream`. No `bedrock:*`, no `resources: ['*']`. These are **inference profile ids** (`jp.` prefixed): a bare foundation-model id fails in ap-northeast-1 with "on-demand throughput isn't supported". The grant must cover the profile ARN **and** every entry in `UNDERLYING_MODELS`; granting only one of the two produces AccessDenied at call time. If you change a `MODELS` entry to a different model family, update `UNDERLYING_MODELS` in the same edit.
- **One IAM role per agent, and `voiceOrchestratorRole` stays on `grantReadData` only.** That read-only grant is the enforcement of the "never on the request path" write rule and of FEATURES §13's per-agent isolation — widening it removes the guarantee invisibly, since nothing else would fail. If a voice feature needs to persist something, the App Runner service (which holds `grantReadWriteData` via `voiceServiceRole`) writes the item off the turn path. Never let one agent role reach another agent's queue, bucket or Lambda, and never collapse the four roles into one.
- **When the App Runner service is added to `compute-stack.ts`, set `VOICE_MODEL_ID` in its env from `MODELS.voiceOrchestrator`.** `services/voice/src/config.ts` silently falls back to a hardcoded profile id while compute-stack pins IAM to whatever `MODELS` says; drift surfaces as an AccessDenied that reads like a permissions problem, not a config problem. Any change to `MODELS.voiceOrchestrator` redeploys `skillbridge-compute` in the same change.
- **Keep the profiler chain shape:** DynamoDB stream → `EventStreamFanout` (filters `EVT#` records, 1-minute `maxBatchingWindow`) → `SkillProfilerQueue` (DLQ, `maxReceiveCount: 3`) → `SkillProfilerWorker`. Never attach the profiler Lambda directly to the table stream — that invokes the async-tier model per record and breaks the debounce the materialized aggregates depend on.
- **Keep `platform: 'WEB_COMPUTE'` on the Amplify `CfnApp`, and declare every app environment variable in `web-stack.ts`'s `environmentVariables` array.** Never set one in the Amplify console: `CfnApp` replaces the whole list on update, so a console value is wiped by the next `cdk deploy` with no diff to show for it. A static `WEB` platform breaks every server route at once. No secrets in that array — Sarvam key and GitHub OAuth token go to Secrets Manager and are referenced by ARN.
- **Before the first Next.js server route ships, add the Amplify SSR compute role in `web-stack.ts`** (set as the app/branch compute role on the Amplify L1) and change `WebStackProps` to take `data.table` — the construct, not `tableName: string` — so the role can be granted read/write. Generally: pass the L2 construct whenever the consumer needs `grant*`; a name string cannot mutate a resource policy. `web/src/lib/ddb.ts` already builds a client for server routes, and `WebStack` creates no role at all, so the first deployed route fails with AccessDenied and the reflex fix is a hand-attached console policy.
- **Add the still-missing pieces as CDK code in their owning stack:** App Runner service → `compute-stack.ts`; Amplify GitHub repo/branch connection (token by Secrets Manager ARN) → `web-stack.ts`; Knowledge Base + vector store and AgentCore Gateway/Identity/Cedar policy store → `ai-stack.ts`. If a resource genuinely has no CloudFormation/CDK support, create it from a committed script — never from the console with nothing checked in. Anything created by clicking is invisible to `cdk diff`, lost on `cdk destroy`, and unreproducible after a teardown.
- **Keep `RemovalPolicy.DESTROY` and `autoDeleteObjects: true` everywhere, and treat all deployed data as disposable.** Every demo asset, seed org, 3D model and KB document must be re-creatable from a committed script or fixture. One `cdk destroy` erases the table (PITR does not survive it), both buckets and the KMS key — and teardown between sessions is how this stays inside a $150 credit budget. Note `*.md` is gitignored, so KB seed documents cannot be committed as `.md`; use another format or generate them.

## Bedrock and agents

- **The agent roster is fixed at four:** voice tutor orchestrator, learning plan generator, assessment scorer, skill profiler. Each keeps its own Strands definition, its own IAM role, its own Cedar policy and its own invocation path. Do not add a fifth — multi-agent breadth beyond these four is PITCH and is the second thing cut under pressure. A new capability becomes a tool on an existing agent. KB ingestion/sync in particular is a pipeline (Bedrock KB sync over the org's S3 prefix, plus an optional quality-flag pass feeding the §4 re-verification warnings), not an agent: no agent role, no Strands definition, no Gateway route.
- **Pick the model by path synchronicity, not task difficulty.** Haiku 4.5 only for the voice tutor orchestrator; the async tier in `MODELS` for the other three (currently Sonnet 4.6 — Sonnet 5 is not entitled on this account, per the comment in `config.ts`). Do not "upgrade" the voice orchestrator for better answers; do not "downgrade" the scorer or profiler for cost. The tiering encodes latency, not quality: only the voice loop makes a human wait on a push-to-talk release. Opus is used nowhere.
- **Nothing but the voice orchestrator may block a response.** Never await an async-tier model call inside a voice turn or inside a Next.js route's response. Skill profiling enters only via stream → fanout → queue; never invoke the profiler directly. Learning plan generation and assessment scoring are triggered on demand but must return before the model finishes: write a pending item, hand work off, let the client re-fetch. No queue exists for those two yet — pick the mechanism, but the handler must not hold the response open.
- **The live voice turn calls Bedrock in-process from the App Runner service under `voiceServiceRole`** — not through AgentCore Gateway, not through a Lambda, not under `voiceOrchestratorRole` (which is `bedrock.amazonaws.com`-assumed and read-only on the table). A Gateway or Lambda hop adds latency to the one path where latency is the product. Orchestrator tools on the turn path read the table only.
- **One Knowledge Base per organization, its data source pinned to `s3://<org-docs-bucket>/org=<orgId>/docs/`.** Never a single shared KB isolated by a metadata filter, and never a data source at the bucket root or at bare `org=`. The prefix-scoped data source is the isolation mechanism; a retrieval-time filter is application-level and fails open. Resolve `kbId` at retrieval time from the verified token's `orgId` — never from a request body, query param or client field.
- **All reasoning goes through Bedrock, authenticated by SigV4 on the task/execution role.** No Groq, no raw Anthropic API keys, no LLM bearer tokens in env or code. `SARVAM_API_KEY` is the only vendor key in the system and is server-side only.

## Voice service (`services/voice`) — Sarvam STT/TTS + Bedrock turn loop on App Runner

- **The voice path is a single persistent Node process holding the browser socket plus both Sarvam sockets at once.** Never port `/voice/stream` to Lambda, API Gateway WebSocket, or a Next.js route handler, and never stand up a second persistent service beside it. A warmed channel lives up to 15 minutes across many turns; no request-scoped runtime holds that. ComputeStack provisions only the ECR repo and task role — the App Runner service itself is created once an image exists.
- **Authenticate from the first frame only:** `{ t: 'start', token }`. Browsers cannot set headers on a WebSocket; do not work around that with a `?token=` query param (leaks into proxy, access and history logs) or the `Sec-WebSocket-Protocol` subprotocol hack (same leak, into handshake logs). See the auth section for how `orgId` actually reaches the token.
- **Implement the upgrade-time guards inside the `upgrade` handler in `channel.ts`:** `Origin` checked against `config.allowedOrigins` before any frame is read, `MAX_SOCKETS_PER_USER = 3`, `MAX_AUDIO_FRAMES = 800` (~40 s stuck-button ceiling). Gate any loopback exemption on `config.isProd === false`, not on the origin string. `attach(server)` takes the `http.Server`: an upgrade is a protocol handshake that never reaches Express middleware, gets no CORS and is not subject to same-origin policy. Without this, any site on the internet can open a socket on a user's token. These constants are declared and currently `void`ed — wire them up.
- **On mid-session token expiry, emit `expired` and close the whole channel** — do not refresh in place, do not end only the current turn. Keep `CHANNEL_MAX_MS` (15 min) and `CHANNEL_IDLE_MS` (5 min) as hard caps. The bounded lifetime is the only thing stopping a revoked or role-changed user from holding a live authorized socket; the client silently warms a new channel, which re-verifies.
- **Gate every `sendText` into the streaming TTS session on `speakable()` (`/[\p{L}\p{M}]/u`).** `bulbul:v3` kills the *entire* reply — not just that chunk — on a message it considers empty (`" "`, `"\n\n"`, `","`, `"."`, `"("`), and streamed model deltas emit exactly those. Text that fails the test is never sent alone and never dropped: concatenate it with adjacent speakable text (ride it along with the preceding word, or hold and merge into the next delta) so it reaches the model only inside a chunk containing a letter.
- **Split reply text on the Devanagari danda `।` as well as `.`/`?`/`!`,** and do not break on a decimal point ("2.5 bar" is one clause). Without danda handling a Hindi reply never splits and collapses into one oversized request. Keep any single synthesis input under ~500 characters, pass only `pace` (v3 rejects `pitch` and `loudness`), and use a v3 speaker — the config default `priya`; v2 names such as `anushka` now 400. On the non-streaming fallback path in `client.ts`, render sentences concurrently and stitch; do not batch several `inputs` onto one request.
- **Use `saaras:v3-realtime` with `endpointing=manual` — never the batch `saaras:v3` endpoint,** which cannot start until audio stops and makes a live mic indistinguishable from a dead one. Audio in is 50 ms raw linear16 PCM, 16 kHz mono, base64 inside the JSON frame (TTS output is 22050 Hz — do not conflate the two). Open both vendor sockets at `begin` (button-down) so their handshakes overlap the question, and **queue** audio frames arriving before the Sarvam handshake completes rather than dropping them: the first half-second is usually where the question starts.
- **Treat an STT partial that is a character-prefix of the transcript already held as a replay and ignore it.** `saaras:v3-realtime` replays a segment from the beginning in fast bursts and re-sends the same partial during silence, so last-write-wins makes the transcript flicker backwards and re-triggers speculation. A partial must never shorten the held transcript, restart speculation, or reset the speculative-start hold timer. Separately: if the final transcript contains no letters at all, send `empty` and end the turn — no Bedrock call, no TTS. Silence is not a question.
- **Every `audio` frame carries the monotonic `seq` from `onAudio(seq, base64Pcm)`, and the client player buffers and plays strictly in `seq` order, never on arrival.** Sentences are synthesised concurrently, so short later sentences routinely finish before longer earlier ones. The server half is forced by the type signatures; the client player is not written yet and is where this goes wrong.
- **Send the transcript to Bedrock verbatim, in whatever language and script it arrived in.** Never pre-translate to English via Mayura — Claude reads Devanagari and Hinglish directly, so a translation hop is pure added latency on the only latency-critical path. Pin the reply language in the system prompt, keep technical terms in English (mask/restore via the `GLOSSARY`), then check the script of the reply's first few words and on a mismatch restart generation **exactly once**. Never loop.
- **Persist transcripts and turn metadata only — never raw audio,** not to S3, not to DynamoDB, not to a disk buffer that outlives the turn. If audio must be dumped while debugging, gate it on `NODE_ENV !== 'production'` and keep it off any bucket. Session metadata goes to `USER#<userId>` / `SESSION#<ts>#<sessionId>`; query and activity events to `USER#<userId>` / `EVT#<ts>#<ulid>` with the 90-day `ttl`. DATA-MODEL puts the TTL on `EVT#` items specifically; do not invent one for `SESSION#`.
- **Do not port `reference/voice-tutor/backend/src/voice/auth.js`.** It does `jwt.verify(token, SECRET, { algorithms: ['HS256'] })` against a required `JWT_SECRET` and then `SELECT banned_at FROM users`. Ours verifies RS256 against the Cognito JWKS via `aws-jwt-verify`. `cognito.ts` already mirrors that file's `verifyToken`/`VoiceAuthError` shape, so the scaffold has half-copied it once. Read `reference/` for orchestration shape (turn overlap, speculative starts, per-sentence TTS); never import from it, never mount it, and never carry over its `llm.js` provider code — it calls Groq/Anthropic HTTP APIs with a bearer key, which is the fastest way to lose the "Built on AWS" story.

## Security and isolation

- **When writing an org document to S3, build the key as `org=<token-derived orgId>/docs/<docId>/<filename>` and name that org's CMK explicitly on `PutObject`:** `ServerSideEncryption: 'aws:kms'` **and** `SSEKMSKeyId: <org CMK>`. `SSEKMSKeyId` alone is not honoured, and the bucket default is the shared `alias/skillbridge-data` key — so an unspecified-key upload silently lands under the shared key instead of the per-org CMK the spec requires.
- **`SARVAM_API_KEY` is server-side only:** injected into App Runner from Secrets Manager, never in `apprunner.yaml`, the Dockerfile, CDK source, a committed `.env`, or any `NEXT_PUBLIC_*` variable. The browser never holds it and never calls `api.sarvam.ai`; its only realtime voice endpoint is this service's `/voice/stream`. No shared-secret HS256 JWT anywhere in the system.
- **Never describe the product as zero-knowledge, end-to-end encrypted, or "we cannot see your documents"** — not in pitch copy, UI strings, README text, code comments or variable names. The model reads org SOPs in plaintext to build the KB and answer from them, so the claim is factually false for this architecture. The claim is exactly three things: encryption in transit and at rest, per-organization isolation, auditability. A false security claim in a judged demo is worse than no claim.
